# Syaahi: student and presentation upgrade audit

Date: 5 October 2026 (India). This document separates verified current capabilities, proposed upgrades and production launch blockers. Suggestions below are a roadmap; they are not claims that all features have been implemented.

## What the project already does

The student workspace has a real foundation: topic/source upload, a reviewable lesson outline, language/detail controls, queued generation, notes, editable pages, PDF styles and export, source references, guided teaching, quizzes, flashcards with saved review schedules, folders, weak-topic results, reminders, shared lessons, tutor chat, audio and interview practice. Keep these flows reliable before adding more navigation or promotional cards.

Presentations are a separate durable workflow. The current model supports cover, points, comparison, process, table and chart layouts; three visual templates; six languages; notes and citations; account ownership; optimistic edit conflicts; worker leases; partial recovery; five-credit charging/refunds; and editable PPTX with native tables/charts and speaker notes. Free users get up to six slides; paid Starter/Pro/Max limits are 8/12/15. The browser preview explicitly approximates PowerPoint layout.

The presentation editor currently uses forms for slide content. Reference input is pasted text, not a full source library. There is no general object canvas in the inspected slide schema. This makes a focused studio redesign more valuable than adding decorative buttons.

## Production findings and fixes

Public probes on 5 October returned 200 for the homepage, `/writing`, `/writer/welcome`, `/writer/membership`, `/writer/support`, `/pricing` and `/presentations`. Both direct Render and proxied `/api/health` returned `ok: true`, `mongo: true`, `role: backend`. Unauthenticated jobs, writer profile and presentation APIs returned 401 as expected. Page HTTP status alone does not prove an authenticated workflow, worker completion or payment settlement.

The hosted billing-region endpoint reported **live** mode and configured one-time checkout. The monthly subscription endpoint reported Starter, Pro and Max **unavailable**. Configuration flags do not validate Razorpay authentication. The exact missing/invalid hosted variables require inspection of the Render service environment.

The locally configured pair is **test** mode and the same pair occurs in the three local environment files inspected. A read-only `GET /v1/plans?count=1` returned 401. Therefore the earlier real-provider smoke failure was a test-key authentication failure; this is not evidence that the separately deployed live keys fail. No order, mandate or charge was created by this diagnostic. A rejected pair can be revoked, mismatched or otherwise invalid; the response does not identify which explanation applies.

This change normalizes credentials across monthly requests, checkout key output and signature verification; normalizes monthly plan IDs; adds a safe 401 operator classification; loads local environment files correctly in the provisioning command; adds a GET-only payment diagnostic; and adds sanitized frontend/backend commit identity for deployment checks. A defensive flashcard change keeps React hooks in a stable order if lesson context becomes temporarily unavailable.

### Finish merchant configuration in this order

1. Inspect the existing Razorpay merchant and the existing Render API service; preserve the account, database and subscription history.
2. Validate a matching key ID/secret in its selected mode with `npm run billing:diagnose`. Use `-- --env-file <private-file>` for an explicit local file. Keys must remain server-only.
3. If the pair is invalid and the original secret is unavailable, the merchant owner must regenerate the pair and update it through a secure configuration flow. Never put the secret in chat, browser-visible variables or Git. Do not replace production live keys with test keys as an incidental diagnostic.
4. Use the existing provisioning preview, `npm run billing:plans`, to confirm the published monthly prices. With a valid test pair, `npm run billing:plans -- --apply` reuses matching plans or creates missing ones. For the live pair, the explicit additional `--live` guard is required. This creates provider plans, not payments; it does not subscribe customers.
5. Set `RAZORPAY_PLAN_STARTER_INR`, `RAZORPAY_PLAN_PRO_INR`, `RAZORPAY_PLAN_MAX_INR` on the API service. They must belong to the same merchant/mode as the key pair. Verify monthly interval 1 and INR amounts 3900/17900/39900 paise respectively.
6. Configure the matching-mode webhook to the canonical `/api/razorpay/webhook`. Its independent signing secret must match Render. Include `payment.captured` and the subscription events the implementation consumes, particularly `subscription.charged` and lifecycle changes.
7. Redeploy with the updated environment, run the read-only diagnostic from the service's private environment and verify monthly availability. Then perform authorized test-mode checkout/cancellation and callback/webhook replay tests. A live charge and settlement remain a separate owner-approved financial test.

`npm run verify:deployment -- --commit <full-sha>` checks the canonical domain's frontend revision and both backend health paths against a single expected commit. Missing revision identity fails that strict check. Vercel system environment variables must be available to expose its supplied commit SHA; Render supplies its commit SHA automatically. An environment update needs a new deploy to take effect on the relevant platform.

Sources: [Razorpay authentication and mode-specific keys](https://razorpay.com/docs/api/authentication/), [Render environment variables](https://render.com/docs/environment-variables), [Render deploys](https://render.com/docs/deploys), [Vercel system variables](https://vercel.com/docs/environment-variables/system-environment-variables).

## Recommended execution order

1. **Stabilise release and payments:** exact deployed revisions; valid matched merchant credentials; correct monthly plans and webhook; role-routing and wallet replay checks. Complete the authenticated lesson → practice → export and deck → edit → PPTX journeys on the hosted application.
2. **Improve daily learning:** Today dashboard, resumable input, clear creation stages, precise citations, practice/exam separation and one due-review queue. Measure completed study sessions and recoverable failures before adding more modules.
3. **Upgrade presentations:** studio shell, outline approval, sources, slide operations, chart/grid editor and preview/export consistency. Keep migrations backward compatible and preserve the existing five-credit/refund contract until pricing changes are explicitly chosen.
4. **Expand after reliability:** deeper mastery/planning, study groups, offline use, presenter mode and collaboration. Each depends on stable identities, source versions and event IDs from the earlier work.

## Release acceptance gates

- A current public page, an authenticated API and both health paths identify the expected release where supported; unknown identity is reported as unknown.
- A student account stays in the student space and a writer account's writer links stay in writer context, including pricing/help/profile deep links.
- Wrong-owner lesson, source, deck, invoice and image requests fail; client-supplied prices/credits never become authoritative.
- Refresh/reconnect/worker restart preserves saved progress and does not double charge. Successful capture credits the same wallet once, including webhook replay.
- Core screens work at 320/390/768/1440px, keyboard-only, reduced motion and zoom; phone tools do not cover the editor or essential actions.
- Actual exported PDFs/PPTX are visually checked, including mixed Hindi/English and dense content. DOM previews alone are insufficient for export QA.
- Provider credentials, document contents and financial response bodies are absent from public diagnostics and logs.

The site responding successfully is useful production evidence. It does not close the merchant, worker, signed-in journey or live settlement gates by itself.
